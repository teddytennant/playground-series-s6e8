§2. THE DESIGN CHANGE TO w26a, AND WHY IT IS A REPAIR AND NOT A DEGREE OF FREEDOM
---------------------------------------------------------------------------------
A1 registers: degrade the 187-member matrix O by adding Gaussian noise at d x the
per-column sd, transform, cross-fit, and read each transform's sensitivity S_k. Q1 says
S_logit is steepest; T1 says H_L is falsified if it is not.

That design HAS A CONFOUND THAT WOULD MANUFACTURE A Q1 PASS. O holds raw member
probabilities and `to_logit` (agent/stack.py:50) clips to [1e-15, 1-1e-15] before taking the
log. Adding raw-space Gaussian noise pushes rows outside the unit interval, and every such
row is pinned to a single constant by the clip. The `logit` transform is the one that eats
that damage undiluted; `rankraw` is immune to it by construction (a monotone rank map),
`rescale` rescales the observed range so it never clips at all, and `hybrid` repairs the 54
worst columns. So the registered noise arm would show logit steepest EVEN IF H_L IS FALSE,
purely as clipping. A test that cannot fail is not a test.

The repair is to run THREE degradation modes and require the ordering to hold across the two
that are confound-free:

  MODE A  SUBSET   -- drop members at random, 187 -> 140 -> 100 -> 70, 2 draws per size,
                     fixed seeds. Perturbs NO value, so no clipping is introduced at all.
                     Every transform here is per-column, so subsetting COMMUTES with the
                     transform and one transform pass serves every size.
  MODE B  LOGITNOISE -- p' = sigmoid(logit(p) + d * sd_logit * eps). Degrades member quality
                     while staying strictly inside (0,1), so it introduces no clipping that
                     was not already there. This is the arm that carries Q3, because it is a
                     genuine per-member quality change rather than a member-count change.
  MODE C  RAWNOISE -- the literally-registered arm, kept and reported so the confound can be
                     MEASURED rather than argued about.

Fit settings: standardised design matrix, C=1.0, tol 1e-4, float64, max_iter 5000, on the
frozen SKF5 seed42 folds. Standardisation is used deliberately: w23 §1 established that the
unstandardised fit stops at ~686 iterations short of convergence while the standardised one
converges in ~65. Comparing SENSITIVITY across four transforms with unconverged fits would
measure how far down the optimiser happened to get on each transform's conditioning, not the
transform's response to member quality. This is a measurement choice about a diagnostic and
touches no shipped artefact.

§3. PREDICTIONS, INHERITED FROM A1 AND SHARPENED
-------------------------------------------------
  Q1  S_logit is the steepest of the four -- IN MODE A AND IN MODE B. Mode C alone does not
      count. If logit is not steepest in both A and B, H_L is FALSIFIED.
  Q2  The ordering of S_k matches the w25f family offsets
      (logit +151.1 > rescale +37.8 > rankraw +15.1 > hybrid +6.1). Rank correlation +1.0
      across four transforms is p = 1/24 under a no-relation null: weak alone, but it was
      predicted before S_k existed.
  Q3  Magnitude, read off MODE B only. The OOF-vs-test member gap is one 5-fold step
      (members trained on 80% vs 100% of rows). If Mode B's slope implies a logit-vs-h3
      advantage of order tens of e-6 for that much quality change, H_L survives; 1e-6 or
      5000e-6 falsifies it.
  Q4  NEW, and it is the confound's own signature: Mode C shows a LARGER logit-vs-others gap
      than Mode B does, and the excess tracks the fraction of rows the clip pins. Registered
      so that if C and B agree, that is evidence the confound is small and A1's original
      design was fine after all.

  raw clip fraction   d=0.00  0.0079   d=0.10  0.0283   d=0.50  0.1216     <- rawnoise

The first row is §2's confound, now measured rather than argued: raw-space noise multiplies

undiluted. Keeping that arm is right, and it is why Q1 excludes it.

The second row is the new problem. `logitnoise` round-trips through logit -> sigmoid, which
lands strictly inside (0,1) and therefore REPAIRS the 0.79% of cells that were already

pre-existing clipping damage, so `logit` would appear to IMPROVE on leaving the baseline and
S_logit would be biased DOWNWARD -- against Q1, i.e. conservative for H_L, but it corrupts
the slope either way.

FIX, applied before any real number existed: the round trip runs at EVERY level of the
logitnoise arm, d=0 included, so noise is the only thing varying along that axis. The d=0
baseline of the logitnoise arm is therefore NOT the shipped matrix and its absolute CV is
not comparable to the subset arm's; only its SLOPE is, which is all Q1/Q2 read. `rawnoise`
is deliberately left unrepaired at d=0 -- carrying the confound is that arm's only job.

F1. WHAT IS BEING ASKED, AND WHY IT IS NOT THE CLOSED QUESTION
--------------------------------------------------------------
RESEARCH closed on 2026-08-13: "tuning ANY GBDT is worth ~4e-7 into the stack --
do not tune GBDTs, do not add ordinary GBDT members." That closure is over KNOBS
inside a fixed loss and a fixed function class, and it was earned twice (LightGBM
tuned for solo AUC, +3e-5 solo = a null; LightGBM tuned for decorrelation, depth
7->3 and leaves 96->8, still maxcorr 0.9961). The generalisation RESEARCH itself
draws from it is the load-bearing sentence:

    "Where a member lands is set by its function class and its pipeline, not its
     hyperparameters."

Neither member here changes a hyperparameter. F1 changes the LOSS; F2 changes the
ADDITIVE EXPANSION. Both are function-class changes of the same kind as w26i's
`max_ctr_complexity 1 -> 2`, which slot 5 accepted for exactly this reason. Every
other flag -- rounds 3200, eta 0.03, depth 7, subsample 0.9, colsample 0.5,
min_child_weight 60, reg_lambda 40, max_bin 512, max_cat_threshold 64, seed 13,
mode latcat -- is held at `xgb_latcat`'s exact value, so each is a ONE-VARIABLE
contrast against a control already on disk (`xgb_latcat`, solo CV 0.9676963).

⚠ ROUNDS ARE FROZEN AT 3200 AND THE PROBES DO NOT CHOOSE THEM. Both objectives
would converge at a different rate and a round-count re-tune would probably help
each member's solo AUC. It is deliberately not done: re-tuning rounds makes each
member a two-variable contrast and re-opens precisely the closed question. If a
later run wants the tuned version, that is a SECOND experiment with its own
control, not a fix to this one.

F2. THE MEMBERS
---------------
F1  `xgb_latcat_l2`    --objective reg:squarederror
    L2 boosting on the 0/1 label instead of logloss. The hessian becomes constant,
    so every row is weighted equally in the Newton step instead of the confident
    rows being down-weighted. Output is not a probability and leaves [0,1]
    (measured -0.076 .. 1.114 on a smoke frame), so it is clipped to
    [1e-6, 1-1e-6] -- one global monotone map applied identically to OOF and test,
    which reorders nothing except exact ties at the boundary and keeps the `logit`
    transform well-defined for the combiner.

F2  `xgb_latcat_dart`  --rate-drop 0.10 --skip-drop 0.5 --one-drop
    DART: each round drops a random subset of the trees already built and fits the
    new tree against what remains, so the expansion is no longer greedy-sequential.
    Set on the `gbtree` booster; xgboost 3.4.0 deprecates `booster=dart` in favour
    of exactly these three parameters. Verified this slot: dropout changes the fit
    (maxdiff 0.111 vs plain at 60 rounds) and inference is deterministic.

⚠ CONSIDERED AND REJECTED: `objective=rank:pairwise`. AUC is a ranking metric so it
is the obvious candidate, and it is rejected on a mechanism this workspace has
already paid for. A pairwise objective has no calibration anchor -- each fold's
model emits an arbitrarily-scaled score -- so pooling five OOF slices into one
vector REORDERS ROWS ACROSS FOLDS. That is the same mechanism that cost -6.2e-5
when five per-fold isotonic maps were pooled. Recorded so no later run re-derives
it, and so nobody reads its absence as an oversight.

§G — w26k: the CT_ train/serve SCALE SKEW in the lattice target-encoding block
Written 2026-08-18 ~02:50 UTC, slot 7, BEFORE any model was fitted for it.
════════════════════════════════════════════════════════════════════════════

G1. THE DEFECT, established from the CACHE ALONE at zero compute cost
--------------------------------------------------------------------
`agent/features.py:te_block` emits, for each of 72 lattice keys, a smoothed target
encoding `TE_k` and the raw cell count `CT_k`. The train part is built with an INNER
4-fold loop (a row never encodes itself); valid and test use the map fitted on the WHOLE
outer training part. That is correct for `TE_` — a smoothed mean is scale-free, and the
measured train/valid difference over all 72 TE columns is 4.10e-4 mean / 1.74e-3 max.

It is NOT correct for `CT_`. A count over 3/4 of the outer-training rows is on a
different SCALE from a count over 4/4 of them. Measured on `cache/f0_*` (means over all
72 CT columns, no model involved):

    ratio valid/train   min 1.3236   median 1.3325   max 1.3382
    ratio test /train   min 1.2802   median 1.3233   max 1.4335

Median 1.3325 against the predicted 4/3 = 1.3333. **Every CT_ feature is ~33% larger at
serve time than at fit time.** A tree learns its split thresholds on the fit-time scale
and applies them to serve-time values, so every CT split is effectively displaced by 33%
of its own value, in a consistent direction, on 72 of 184 columns.

G2. SCOPE — this is UPSTREAM, not ours
--------------------------------------
`data/oof/src/train_lattice.py` (szymonkapiski's public 47-model OOF library, from which
`agent/features.py` is adapted and which the donmarch14 CatBoost family also descends
from) has the identical construction at its lines 172-194: `oof_ct[hi]` from the inner
`g["count"]`, `ova`/`ote` from the full-train `g["count"]`. So the skew is in the public
lattice recipe, and every `lat_*` member in the library carries it, as does every own-
built `lat`/`latcat`/`natlat` member here, since 2026-08-10 when `cache/` was written.

G3. THE INSTRUMENT — one fit, many predictions, exactly paired
--------------------------------------------------------------
A per-feature affine rescale of a tree model's INPUT is equivalent to rescaling that
feature's THRESHOLDS: multiplying the train CT by s and refitting gives (up to binning
ties) the same row partition with thresholds scaled by s, which is the same function as
the ORIGINAL model applied to serve data with CT divided by s. So the correction needs
NO refit. Fit `lgbm_fixed_lat`'s exact config once per frozen fold, then emit one OOF
slice and one test column per scale

    s in {1.0, 1.1, 4/3, 1.5, 2.0}      (predict on Xb, Xt with CT columns / s)

s = 1.0 is the status quo. s = 4/3 is the pre-registered fix. The arms share the identical
trees, the identical rows and the identical folds, so nothing separates them except the
serve-time CT scale — the "matched on everything except the thing being tested" rule that
this workspace has been caught by three times.

G4. THE REGISTERED PRIOR — a small POSITIVE effect, and the DIRECTION is the real claim
---------------------------------------------------------------------------------------
CT is a *precision* channel: the model uses it to decide how far to trust the TE beside
it. Inflating it 33% at serve time makes the model over-trust thin cells on rows in a
band around each learned threshold. The dynamic range of CT is huge (0 to ~30k), so
log(4/3) = 0.29 nats is a small displacement against it and MOST splits will not change
which side a row falls on. Registered:

    s = 4/3 minus s = 1.0, member solo OOF AUC     0 to +200e-6, modal +30e-6
    the same pair, marginal into the 187 pack      0 to +3e-6, modal ~0
    argmax of the s-curve                          at or near 4/3, NOT at 1.0

⚠ The curve's ARGMAX is selected on the same OOF that scores it; this workspace has
measured arm-selection optimism at +1.78e-6 and it must not be spent twice. **The primary
readout is the pre-registered point s = 4/3 against s = 1.0, and nothing else.** The rest
of the curve is MECHANISM evidence only: if the skew is what is being corrected, the curve
should rise from 1.0, peak near 4/3, and fall away by 2.0. A curve that is flat, or that
peaks at 1.0, is a null and must be written up as one.

G5. THE NAMED FAILURE MODES, registered before the number exists
----------------------------------------------------------------
(a) **A null is the modal outcome for the PACK even if the member gains.** RESEARCH's
    standing finding is that the pack's span already contains what the 12 columns can say
    and that a new member is worth ~0. A member-level gain of +30e-6 that buys +0 into the
    pack is CONSISTENT with everything on file and is not a disappointment; it must be
    reported as a member-level result, not as a stack result.
(b) **Thread-count nondeterminism is NOT a reproduction failure.** `lgbm_fixed_lat` was
    built at `n_jobs=-1` and scored CV 0.9677108350221775; this runs at fewer threads
    because the box is contended, and LightGBM's histogram reduction is not guaranteed
    bit-identical across thread counts. The s = 1.0 arm is therefore compared to that
    stored CV as a SANITY check with a 5e-6 tolerance, and the A/B claim rests entirely on
    the within-run pairing, which shares one set of trees and cannot be affected by this.
(c) **If s = 4/3 wins, that is a claim about the FEATURE, not about LightGBM.** It must be
    replicated on a second function class before `te_block` is changed for good; a single
    family is one reading, which is the "three replications are ONE reading" error.

G6. ADDENDUM — the TE re-shrink arm, registered before its first number exists
------------------------------------------------------------------------------
Added 2026-08-18 ~03:35 UTC while `w26l_serve.py --name r400` was still on fold 0 and had
printed no AUC of any kind. It covers the `te` and `both` arms, which §G3-G5 did not.

The second skew (RESEARCH w26 slot 7 §4): `TE = (S + lam*gm)/(n + lam)` is smoothed against
a 3/4-size count at fit time, so the train TE is shrunk MORE toward gm than the serve TE of
the same cell. Measured, and concentrated in thin cells as the algebra requires: sd(valid)/
sd(train) 1.0293 over the 12 thinnest keys, 0.9933 over the 12 densest. The corrector
inverts the smoothing and re-shrinks at f = 3/4; it cuts mean |sd ratio - 1| from 0.008992
to 0.002992 and independently recovers lam = 20 from the cache, a constant recorded nowhere
on disk.

⚠ **The sign here is NOT obvious, unlike the CT arm, and that is registered.** Two readings
compete and only one of them favours the correction:

  (a) skew reading -- the model was fitted against shrunk TE and is served un-shrunk TE, so
      it is extrapolating past its training support. Correcting is a pure win.
  (b) information reading -- the serve TE is estimated from 4/3 as many rows and is simply a
      BETTER estimate of the cell rate. Re-shrinking it deliberately throws that away to
      match a fit-time artefact. Under this reading the correction LOSES.

Registered priors, deliberately wider and less committed than G4's:

    te   minus ct1.0     -60e-6 to +60e-6, modal +5e-6, sign genuinely uncertain
    both minus ct1.3333  -60e-6 to +60e-6, modal ~0    (i.e. TE adds ~nothing on top of CT)

⚠ **`both` must be judged against `ct1.3333`, not against `ct1.0`.** Judging the combined
arm against the uncorrected baseline would credit the CT fix twice. The CT fix is the
pre-registered headline; the TE arm's only question is what it adds ON TOP of it.

⚠ The sampling-noise half of the TE mismatch (a 3/4 subsample carries sqrt(4/3) = 1.155x the
sd of a full one) is NOT correctable and is NOT attempted. If the `te` arm is a null, that
does not show the shrinkage analysis is wrong -- it shows the systematic half is too small
to matter next to the noise half, which is a different and weaker claim, and must be written
up as the weaker one.

--------------------------------------------------------------------------
Written 2026-08-18 ~03:50 UTC. `w26k_ctscale.py` (2000 rounds, the exact `lgbm_fixed_lat`

    100 rounds   ct1.0 0.958712 -> ct4/3 0.958829   +117e-6
    400 rounds   ct1.0 0.964779 -> ct4/3 0.965104   +325e-6

Mechanism, if the skew story is right: more rounds means more splits on the CT block, so

G8. THE MISSING CONTROL, named now so the next run does not skip it
--------------------------------------------------------------------
If correcting the CT scale is worth +3e-4, the obvious rival explanation is that the CT block
is simply NET-HARMFUL as built, and that anything which neutralises it would score the same.
The control that separates those is **drop the 72 CT_ columns entirely and refit** (`ct_drop`).

  - `ct_drop` ~ `ct1.0`      -> the CT block was doing nothing either way; the fix is real
                                and it is repairing a channel that does carry signal.
  - `ct_drop` ~ `ct1.3333`   -> the block as built is net-harmful and the honest
                                recommendation is DELETE IT, not rescale it. Simpler, and it
                                would transfer to the public library without needing anyone's
                                model.
  - `ct_drop` > `ct1.3333`   -> the fix is a partial repair of something better removed.

⚠ Unlike every arm in §G3, this one CANNOT be done with the saved boosters -- dropping a
feature changes the fitted trees, so it needs its own fit. Budget for it; do not substitute
"set CT to a constant at serve time", which is a different intervention (it keeps the split
structure and merely sends every row down one side) and would answer a different question.

⚠ Registered prior, before it is run: `ct_drop` lands BETWEEN `ct1.0` and `ct1.3333`, nearer
`ct1.0`. Reason: the block's total gain share measured 0.2% on the 100-round probe -- small,
but the fix is worth +3e-4, so the channel is not inert. Modal guess `ct_drop - ct1.0` =
+100e-6, i.e. about a third of the fix.
